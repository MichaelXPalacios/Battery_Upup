## 3. How D1a, D1b and D2 call it

All timestamps are tz-aware UTC pandas Timestamps; a naive timestamp raises. Run from `hugging-base/dispatch/` with `PYTHONIOENCODING=utf-8`.

**D2 (service, guard, monitoring)**
```python
from dispatch.features import online
from dispatch.data import catalog, flows, prices

online.read_latest(sp, *, client=None) -> (df, asof_utc, max_published_utc)    # raises online.FeaturesMissing (a LookupError) or online.OnlineStoreError
online.write_latest(sp, df, *, client=None, ttl_s=None) -> None
online.refresh_latest(sps, asof_utc=None, *, store=None, log=...) -> {sp: {"asof_utc", "max_published_utc", "rows"} | {"error"}}
flows.prepare_signal(sps=DEFAULT_SPS, *, now_utc=None, ingest=True, min_ingest_gap_s=20.0, report_ids=None, store=None, fetcher=None, log=...) -> dict
catalog.freshness(now_utc=None, report_ids=None) -> {report_id: age_s}
prices.price_source(spec, start_utc, end_utc, *, asof_utc=None, include_dam=True) -> PriceFrame    # raises prices.PricesNotPublished (a LookupError)
```
* `read_latest` returns the frame `build.point_in_time` made: index `interval_start_utc` (96 rows, tz-aware UTC), columns `sets.FEATURES` (41 model inputs) then
  `settlement_point`, `asof_utc`, `max_published_utc`. `FeaturesMissing` now derives from `LookupError` as D2 asked.
* **Who refreshes the online features.** Nothing schedules itself. Whatever triggers a signal calls `flows.prepare_signal([spec.settlement_point])` once per cycle, right before `POST /signal`: it pulls what
  ERCOT just posted (every live report: 8 listings, only new files), parses what changed, then `online.refresh_latest(sps)`. Measured on the real lake: `prepare_signal` for one hub takes 4.3 s (2.0 s of it the eight listings when nothing is new, the rest building and writing the frame), for all five hubs 6.4 s; the first call after an hour's gap fetches and parses what is new (8 to 12 s); importing the package adds 2 to 5 s once. It ingests ALL live reports, not only the four the features read, because D2's stale-data monitor also watches NP6-331-CD, NP6-322-CD and NP6-86-CD; pass `report_ids=flows.FEATURE_REPORTS` for the lean version. A failed fetch does not block the refresh (the frame is built from what the
  lake has and the age gate decides). A background loop `python -m dispatch.data.flows ingest --online` every minute keeps the lake and Redis warm in between (and is the only way to keep NP6-322-CD inside D2's 10-minute allowance if signals are 15 minutes apart), but it does NOT replace the call before the signal: the stored frame's first
  row is the interval containing `asof_utc`, so a frame built before a 15-minute boundary is one interval behind after it (the guard then answers `interval_out_of_window`).
* **What "feature age" is.** D2's gate is `now - max_published_utc`. That is the newest ERCOT publish time among the inputs, not the build time, so refreshing does not make it younger. See section 7 for what it looks like on the real feed.
* `price_source` is what D2 asked for: a DataFrame on the 15-minute UTC grid `[start_utc, end_utc)`, index `interval_start_utc`, float64, columns `rt_usd_per_mwh`, `dam_usd_per_mwh` (left out if any hour is missing) and
  `as_<product>_usd_per_mw_h` for every product in `spec.as_products`. It raises `PricesNotPublished` unless every interval has a price (RT price: `rt_spp` before the archive, latest published version; AS: the 15-minute RT MCPC where it exists,
  else the day-ahead MCPC of the hour; a product with no price yet at that time, ECRS before 2023, is priced 0). `asof_utc` hides rows published after it.

**D1a (models)**
```python
from dispatch.features import build, sets
build.training_frame(sp, start_utc, end_utc, decision_every="4h", *, horizon=96, context=None, offset="0min") -> (X, y, decision_utc)
build.point_in_time(sp, asof_utc, horizon=96, *, context=None) -> DataFrame
build.read_offline(sp, start_utc=None, end_utc=None, version="1.1.0") -> (X, y, decision_utc)       # the stored copy of training_frame
build.write_offline(sp, start_utc, end_utc, decision_every="4h", *, version="1.1.0", offset="0min", log=...) -> [Path]
build.decision_times(start_utc, end_utc, decision_every="4h", offset="0min") -> DatetimeIndex
sets.FEATURES        # the 82 model inputs, in order (the 41 of 1.0.0, then the 41 of notes/d1a.md section 10);  sets.FEATURE_TABLE has dtype, group, description and publish rule of each
from dispatch.features import compat
compat.for_forecaster(df, forecaster) -> DataFrame     # df with the names the model was trained on: renamed for interim_d1a/v1 models, df itself for a model trained on rt_v1 names
compat.to_model_names(df, names=None) -> DataFrame     # adds the interim-named columns (rt_mean_4, tgt_hod, as_regup_dam, ...) to an rt_v1 frame
```
* `X` has a `RangeIndex`; columns are `sets.FEATURES`, then `settlement_point`, `asof_utc`, `interval_start_utc`, `max_published_utc`. `y` is the realised RT SPP ($/MWh, float64) of the target interval, the label, never a feature.
  `decision_utc` equals `X["asof_utc"]`. Rows with no known RT price at the decision, or no realised target price, are dropped. Fit on `X[list(sets.FEATURES)]`.
* **Horizon.** `horizon` 1 is the interval CONTAINING the decision (`floor_15min(asof)`), 2 the next, ... 96 starts 23.75 h later: the same convention as `quantile.horizon_steps` and the guard.
* Decision times are multiples of `decision_every` from the Unix epoch plus `offset` (default 0), so the grid does not depend on `start_utc`. The default grid sits on interval boundaries, where the newest known price is always 15 minutes old;
  `offset="7min30s"` trains on other ages, closer to a service that decides at any second.
* `point_in_time` and `training_frame` run the same code (`build._compute`), and tests prove the rows are identical bit for bit, whatever range the context was loaded over, so a model sees the same features in training and at the service.
* **The 41 columns of your section 10 are in, under your names** (`rt_prof7_med`, `res_q90_672`, `dam_as_<p>_med14`, ...), and equal your interim builder's numbers exactly on the 4-hour grid (section 15). The registered `research` model (`interim_d1a/v1`) names its inputs the interim way, so serve it with `compat.for_forecaster(df, forecaster)` (the service already does: `deps.adapt_features`, wired in `service/wiring.py`, called in `cycle.py` before `predict`); a model trained with `--source d0` needs no rename. `train.choose_source` now picks D0 by itself.

## 5. When did each row become public?

A row may feed a decision at `asof_utc` only if `published_utc <= asof_utc`. Where ERCOT puts the posting time in the file name it is REAL. Historical files that carry none get the named rule below, always conservative (assume LATER),
and every assumed time is also capped at the posting or fetch time of the file that holds it. Constants: `dispatch/data/assumptions.py` (REQUEST to move them into `config.py`, section 13).

| dam_spp, dam_as | NP4-190-CD, NP4-188-CD | file name. Measured over 32 days: results for day D post on D-1 between 12:32 and 13:55 CPT. **The 13:30 CPT in the brief was missed on several days**, so it is not used | REAL |

**Daylight saving (tested).** MIS file names carry Central Prevailing Time with no offset, so on the November fall-back Sunday the hour 01:00 to 02:00 is ambiguous. Rule: an ambiguous time is read as the SECOND occurrence (standard time, the
LATER UTC instant). A file can then only look published up to an hour late, never early, so the rule cannot create leakage (`assumptions.MIS_AMBIGUOUS_IS_STANDARD_TIME`). If the JSON listing's offset-bearing `PublishDate` is available it decides instead.
A non-existent spring-forward time is read as standard time too (02:30 -> 03:30 CDT). Data rows use ERCOT's own repeated-hour flags (`DSTFlag`, `RepeatedHourFlag`), so a 25-hour day has 100 distinct 15-minute instants and a 23-hour day 92 (tested).

**Why the archive rows are not published at the archive's posting time.** The yearly workbook is a bulk copy of prices that were public minutes after each interval; stamping them with the workbook's posting time would make 15 years of history
"unknown" until the day it was posted. The assumed per-row times above are the earliest defensible ones that are still later than the measured real ones.

* **Point in time.** Two rules, both in `build.py` and nowhere else. `_known_prefix`: prices, gas, weather days and the operating dates of the day-ahead prices arrive in order, so what is known at asof is a prefix of the series (a late row hides everything after it until it is published; windows, lags and profiles only read inside the prefix; a date or a day without rows hides nothing and is never "the newest"). `_visible`: row-wise lookups (DAM price and ancillary price of the target hour, the rows of the 14-date median, load forecast issue) need `published_utc <= asof`. Every row carries `max_published_utc`, the newest publish time of anything that fed it. With publication in order, a lake that holds the future gives the same frame as a lake cut at the decision time (tested for all 82 columns); with a late row in it, the frame is more conservative (section 12).
* **Duplicates.** If an interval was published twice the features use the EARLIEST published version (what was known soonest); the label `y` uses the LATEST (what settled), REAL before ASSUMPTION in both.
* **Offline store.** `features/rt_v1/1.1.0/sp=<sp>/part-YYYY-MM.parquet`, one file per month of decision time, columns `settlement_point, asof_utc, interval_start_utc, max_published_utc, <82 features>, y_rt_usd_per_mwh`. The 1.0.0 store was deleted (derived data). Footer metadata: feature set, version, schema hash, decision cadence, offset, month, rows.
* **Online store.** Key `dispatch:features:latest:<sp>` (`config.FEATURES_LATEST_KEY`), ONE JSON value, only SET/GET/DEL/EXPIRE (Redis 3.0 safe), about 62,667 to 65,638 bytes (96 rows x 85 columns) per point. Strict JSON (NaN is `null`). The client must speak RESP2 (`protocol=2`): redis-py 8 opens with `HELLO`, which Redis 3.0 rejects. `online.connect()` does that and reads `config.REDIS_URL` (now :6390).

* **Window arithmetic does not depend on the range loaded** (`features/windows.py`). Means and deviations are elementwise IEEE additions in a fixed order (oldest value first) over the window gathered from the context; quantiles, medians and extremes come from a sort. The same decision therefore gives the same bits in `training_frame` over any range, in `point_in_time` and in any rebuild (tested: the same 672 values cut out of long and short arrays give identical results; the deviation agrees with exact arithmetic to 1e-12). pandas' `rolling` (used in 1.0.0) keeps a running sum, its low bits depend on where the loaded array starts, and its deviation lost digits after a $9,000 spike. Dropping it also made the five-hub offline build three times faster (151 s, 436 s before).

## 11. Findings about the environment

* **Redis.** :6379 belongs to another application and is full (108 MB of a 100 MB `maxmemory`, noeviction): every write fails. Not touched. The platform now has :6390 (append-only, 256 MB); `online.connect()` reads `config.REDIS_URL`.
  redis-py 8.1 must be told `protocol=2` for Redis 3.0.504 (`HELLO` is unknown). `online.FileStore` is a same-interface fallback that writes `features/online/<sp>.json`; it is not the default.
* **Windows.** Every `open()` costs about 10 ms here (real-time file scanning), so `lake.put` reads the source once, writes outside the catalog lock and keeps the lock and append handles open: 15 ms per file (6 ms with 8 threads) against 98 ms before.
  Paths top out at 260 characters: keep `DISPATCH_HOME` short (the default is 55). The lake files carry the read-only attribute; delete a test lake with PowerShell `Remove-Item -Force`, not `rm`.
* **Memory.** 9.9 GB total, about 3 GB free: `parse` runs two worker processes (`workers=2`). Four gave no speed-up (the 18 yearly workbooks took 10.7 min with four workers, against about 12 min in one process). `multiprocessing` is not used: on Windows it re-imports the caller's `__main__`, which breaks any script without a
  `__main__` guard (it broke my own driver), so the workers are `python -m dispatch.data.parse --group <dataset> <group>` subprocesses.
* **No openpyxl.** `data/xlsx.py` reads the OOXML directly (vectorised fast path, about 20 s per 600k-row workbook, plus a general fallback). It copes with the stray summary row ERCOT leaves at the end of some October sheets, with date columns that

## 12. Known limits

* Revisions are not modelled: features use the first published version, labels the latest.
* The nodal history is short (section 4); the yearly archives cover hubs and zones only.
* Weather and gas are stale by 10 to 11 days until someone fetches NCEI and FRED again (no fetcher written; not requested).
* The weather forecast snapshots are collected from now on (NWS keeps no archive) and are NOT a feature of `rt_v1`; a forecast feature needs weeks of snapshots first.
* Zone mapping for weather and load forecast is approximate: a settlement point follows the weather stations and weather zones of its load zone (`data/weather.py`, ASSUMPTION), hubs follow their namesake zone, system hubs follow the system index.
* LZEW / LZ_DCEW rows are kept in `rt_spp` and `rt_spp_hist` (column `sp_type`) and dropped in the `*_all` views and the builder, which would otherwise see two prices for one name.
* `ingest_once` takes only `_csv.zip` files; the xml twins are ignored.
* One writer per lake for the catalog append is guaranteed (lock file); `parse` workers write disjoint partitions.
* The prefix rule is conservative, not a pure function of the rows published by asof: if an interval (or an operating date of day-ahead prices) is published AFTER a later one, a lake that holds it hides the later ones until it is public, whereas the live lake, which does not hold it yet, shows them. ERCOT publishes in order (the worst case seen is a file 507 s late, followed by on-time files that were not published before it), so this never happened in the data; the effect would be a training frame with a little less information than the live frame, never more.
* Served at an arbitrary second, D0's newest RT price is usually one interval fresher than the interim assumption D1a trained under (public 30 minutes after the interval starts; the MIS file arrives about 17 minutes after it starts). No leak, but the models see fresher inputs than in training; on the 4-hour grid, where the models were trained and evaluated, the two agree exactly.
* The 60-day datasets cover 42 operating days (1 Jul to 11 Aug 2026) and become public 60 days late, so they serve analysis and attribution, not live features.

**Where the two builders differ by design, and which is right** (none of it moves a number on the grid above):
* `rt_std_24h/7d` (sample deviation in 1.0.0) and `is_holiday` (the weekend date also flagged): not leaks, a choice of definition. 1.1.0 follows the models (population deviation, observed holiday only), see section 6.

* **RT price publication.** The interim builder: public 30 minutes after the interval starts. D0: the file-name time (about 17 minutes after the start) or, for the archive years, the end of the interval + 10 minutes. Off the grid D0 sees the newest price one interval earlier than the interim builder in part of the minute-by-minute cycle; on it they agree. Not a leak; D0's times are measured.
* **A missing interval inside a window.** The interim builder forward-fills it, the spec (and D0) skips it. No window of the four hubs contains one (their 15-minute price series are complete from 1 Jan 2019 to 20 Sep 2026: 270,624 slots each, none missing, checked directly), so no difference shows; where one appears D0's rule invents nothing.

### What the new tests found

The cut-the-lake test caught two defects that the history comparison could not (the full lake always holds the rows after a historical decision), both in the ONLINE case and both fixed: (1) at a decision after the daily day-ahead publication the newest operating date is TOMORROW, whose rows were beyond the hourly grid of the context, so the median was
taken over 13 dates instead of 14; the grid now reaches two days past the last target; (2) an operating date with no rows in the lake yet (tomorrow, before 13:00) was taken for "the newest date", shifting the window; the newest date is now the newest one that has rows (`AsMatrix.lastrow`), while a date without rows still counts as a date of the window. The day-ahead rows are also read 14 days
earlier, so a stale newest date (a publication outage) still has 14 dates behind it.
