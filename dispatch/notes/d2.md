## 2. The cycle

`service.cycle.run_cycle(asset_id, now_utc=None, deps=None) -> ServiceCycleResult` (a `CycleResult` plus `latency_s`, `plan_id`, `detail`,
`proposed`). `deps` is a `CycleDeps` (assets, halt flag, ledger, audit, online store, forecaster, optimizer, guard, metrics, clocks). With no
`deps` it builds the real ones (`wiring.default_deps()`). The same function serves a live request, a replay (`now_utc` = decision time) and
the Gate 3 harness (`replay_cycles`). It never raises.

```
POST /signal {asset_id, now_utc?}
  1  halt flag (Redis)            set, or Redis unreadable           -> halted
  2  asset + ledger               unknown asset, ledger cannot start -> error
  3  latest features              missing / older than 15 min        -> stale;  published after now, bad frame, store down -> error
  4  forecaster.predict           leakage check on max_published     -> error (no_model, forecast_failed/invalid/leak)
  5  optimizer(spec, P50 view, soc0, mode="forecast")                 -> error (optimizer_unavailable/failed, plan_not_optimal)
  6  setpoint = first interval of the plan (same maths as lp.first_setpoint; a test proves they are equal)
  7  halt flag AGAIN, then guard.check(...)                          -> rejected | halted | error
       audit: signal + guard_decision are on disk BEFORE anything executes
  8  PaperLedger.record (re-checks power, AS, SOC limits itself)      -> dispatched | error (ledger_refused)
  9  audit setpoint + cycle summary; metrics (histogram, counters, gauges)
```

soc0 is the paper ledger's SOC at the start of the plan's first interval; D1a's features start at the interval that contains the decision.
The ledger is the SOC source in paper mode (age 0). Latency is a monotonic clock around the whole cycle (`dispatch_cycle_seconds`).

Fail-closed paths, each with a test (`tests/test_api.py::test_fail_closed`, 21 cases, plus the API-level ones):

| Condition | status | reasons |
|---|---|---|
| halt flag set / Redis unreachable / flag unreadable / kill arrives mid-cycle | halted | halted |
| features missing, empty frame, D0's `FeaturesMissing` | stale | features_missing |
| features older than `MAX_FEATURE_AGE_S` (900 s; exactly 900 passes) | stale | features_stale |
| features or forecast published after the decision time | error | features_from_future, forecast_leak |
| online store raises / not wired | error | feature_read_failed / online_store_unavailable |
| no model holds the alias | error | no_model |
| the loaded model's alias was cleared or moved to another version (checked every 30 s with `registry.aliases()`) | error | model_stale |
| forecaster raises, NaN in P50, wrong settlement point, empty version | error | forecast_failed, forecast_invalid |
| optimizer raises / not wired / status not optimal | error | optimizer_failed, optimizer_unavailable, plan_not_optimal |
| guard rejects (power, SOC, AS, exposure, ...) | rejected | the guard's codes |
| guard raises | error | guard_error |
| audit log cannot be written | error | audit_failed (nothing executes) |
| ledger refuses (stale interval, issue time, limit re-check) | error | ledger_refused |
| another cycle for the asset is running / deadline (120 s) passed / bad `now_utc` / unknown asset | error | cycle_in_progress, deadline_exceeded, invalid_time, unknown_asset |
| anything unexpected | error | exception |

Every one of them writes a `cycle` audit record with the status and reasons, and moves `dispatch_cycles_total{status}`
(`test_the_audit_trail_names_the_reason_for_every_failure`). `/signal` answers 200 for dispatched, rejected, halted, stale and 503 for error.

## 3. The guard (FR8)

`guard.check(spec, setpoint, state, *, now_utc, limits=DEFAULT_LIMITS) -> GuardDecision`. Pure: no I/O, no clock. `now_utc` is a required
keyword (DESIGN.md's signature has none). It rejects, and returns the caller's setpoint object unchanged when it accepts. Any exception
inside it is a rejection (`guard_error`). All applicable codes are returned, in this order:

| Code | Rejects when |
|---|---|
| halted | `state.halted` is anything but a plain `False` (a string "false" halts) |
| model_version_missing / asset_mismatch | empty model version / setpoint for another asset |
| non_finite / malformed | NaN or inf anywhere (spec, setpoint, state), a wrong type (checks stop here) |
| interval_invalid / interval_out_of_window | naive or NaT time / interval not the current or the next 15-minute interval of `now_utc` |
| soc_stale / soc_telemetry_invalid | `soc_age_s` > `MAX_SOC_AGE_S` (300 s) / SOC reading outside [0, energy_mwh] |
| power_limit | abs(net_mw) > power_mw |
| as_negative / as_product_unknown | award < 0 / product not in `spec.as_products` |
| as_up_power / as_dn_power | discharge + up awards > power, charge + REGDN > power (only when an award is present) |
| soc_above_max / soc_below_min | projected end-of-interval SOC outside [soc_min, soc_max] |
| as_up_energy / as_dn_headroom | sum(dur_k r_k) / eta_d > soc_end - soc_min for REGUP, RRS, ECRS, NSPIN; eta_c dur r_REGDN > soc_max - soc_end |
| exposure_cap | `state.exposure_usd` > `exposure_cap_usd` |

Formulas are D1b's (`lp.py` states the same constraints; `lp.check_plan` is the same test). `soc_end = soc0 + eta_c*charge*dt -
discharge*dt/eta_d` with the spec's `eta_charge`/`eta_discharge` and `DT_RT_H`; durations are `AS_DURATION_H`. All arithmetic goes through
`dispatch.units`. Decisions and their reasons:

* **Tolerance, not clipping.** DESIGN.md allows clipping within `GUARD_EPS_MW`. Clipping the combined constraints has no canonical
  answer (which award do you shave?), so the guard treats a violation of at most `GUARD_EPS_MW` (1e-6 MW) or `GUARD_EPS_MWH` (that
  held for 15 minutes, 2.5e-7 MWh) as met and never edits a value. What the audit log shows as proposed is exactly what the ledger executes.
* **AS energy is checked on the end-of-interval SOC**, the way the LP states it. Also checking the start of the interval would reject plans that
  ramp an award up while charging. Verified on 60 consecutive real LP plans with awards (below): zero rejections.
* **Exposure** (the guard only compares two numbers; the cycle supplies them): the cost basis of the energy in the battery, after the setpoint,
  charging priced at the P90 RT forecast of the first interval (or `ERCOT_PRICE_CAP` if there is none), energy the battery starts with free,
  discharging releasing its share of the cost. Cap: `exposure_cap_usd` per asset ($25,000 for the pilot, ASSUMPTION). A setpoint whose exposure after the trade is above the cap is rejected,
  including a discharge that reduces the exposure but not enough: fail closed, the operator raises the cap. This is the weakest-defined limit; see section 12.

Evidence for "Guard integrity: zero" (`tests/test_guard_props.py`, 48 tests): an oracle written in the test recomputes every invariant from first
principles (literal NPRR1282 durations, no `dispatch.units`, no guard helpers). The generator is checked to reach both outcomes (about a third of the cases are accepted)
and at least 14 reason codes, so the soundness test is not vacuous. Run at `GUARD_PROP_EXAMPLES=20000` (15 minutes), 0 failing:

| Property | Examples |
|---|---|
| every accepted setpoint satisfies every invariant (soundness), a setpoint comfortably inside every limit is accepted (completeness), a violation beyond tolerance is rejected (agreement) | 20,000 |
| a set halt flag always rejects | 6,666 |
| the halt flag is fail closed for anything but a plain False (True, None, "false", 0, 1, "", "no", NaN) | 3,333 |
| garbage (NaN, inf, wrong types, naive times, nonsense AS maps) never raises and is never accepted | 10,000 |
| well-typed NaN/inf/1e308 inputs are rejected for a reason, never by a guard bug | 10,000 |
| tightening any of 11 limits (power, SOC floor and ceiling, energy, AS products, exposure cap and exposure, SOC age and its limit, tolerance, halt) never turns a rejection into an acceptance | 20,000 |

About 70,000 passing examples in total. The default run (`GUARD_PROP_EXAMPLES` unset) uses 1,500 per main property and takes about two minutes. Plus the worked examples: one per reason
code, the exact boundary of each limit, current and next interval, the split and charge loss conventions, the NPRR1282 durations.

## 4. Execution and audit (FR9, FR10)

* **Paper ledger** (`runtime/ledger/ledger-<asset>.jsonl`, append only). `init` line, then one `setpoint` line per accepted setpoint with the SOC
  before and after, the cost basis and the audit hash of the guard decision that allowed it. A later setpoint for the same interval supersedes the
  earlier one (both stay in the file). A setpoint for an older interval, or one whose `issued_utc` does not move forward, is refused; resubmitting an
  identical one is a no-op. `record` re-checks power, AS and SOC against the SOC the ledger itself holds, so a guard that saw a different SOC cannot
  get a setpoint executed. `settle(spec, prices)` = energy $/MWh x MWh + AS $/MW-h x MW x h - wear, all through `dispatch.units`, and a test proves it
  equals `lp.account` for both loss conventions. `replay(spec, prices, start, end)` re-simulates the period FROM THE FILE and reports any difference
  from what the file says. `as_actual(spec)` gives D1b's attribution engine an `ActualDispatch` (source `paper-ledger`).
* **Audit log** (`runtime/audit/audit-YYYYMMDD.jsonl`). One JSON record per line, SHA-256 chain across daily files: `prev_hash`, `hash` over the canonical JSON
  of the record. `append(event) -> hash`, `verify() -> (ok, first_bad_line)`. Fsynced before it returns. Types: signal, guard_decision, setpoint,
  cycle, kill, resume, halt, error, model_load, breach, retrain_request, gate3, startup. Editing, deleting, inserting, reordering, blanking a line or tearing
  the tail is detected at the line (and a Hypothesis test mutates random bytes of the file: any change in content is detected). A cut-off tail is invisible
  to a bare chain, so `head()` is also kept as an anchor in Redis and `verify(expected_head=...)` fails if the log is behind it. `AUDIT_RETENTION_DAYS = None`:
  retention is the PRD's open question and nothing here deletes anything.
* **QSE adapter** (`qse.py`): the Protocol, `DisabledQSEAdapter` (refuses every call), `ENABLED = False`, `get_adapter()` refuses to hand out anything else.
  A test checks that no module of `dispatch/service/` mentions it.
* **Crash story.** The guard verdict is written to the audit log before the ledger write. If the process dies between the two, the next start
  (`service/reconcile.py`) finds the accepted decision with no `setpoint` record and no ledger line, and writes an `error` record for it, once.

## 5. State, API, wiring

* `RedisHaltFlag`: key `config.HALT_KEY`, JSON `{reason, set_by, set_utc}`; client injectable; unreachable = halted. A kill made while Redis refuses writes is held
  in the process and written back when Redis answers. `writable()` probes with a scratch key (cached 30 s).
* Wiring (`service/wiring.py`) binds `features.online.read_latest`, `registry.mlflow_registry.load` (and `.aliases`, for the stale-model check), `optimizer.lp.solve`, `attribution.engine.attribute`,
  `data.catalog.freshness` at startup, never at import. Missing or raising, a target becomes None with its error text; `/health` shows each; `/signal` fails
  closed with the reason. As of this writing all six bind.
* API (`service/app.py`): `/signal`, `/kill`, `/resume` (added: audited, refuses while Redis is down or the audit chain does not verify), `/health`, `/metrics`,
  `/attribution`. Optional bearer token (`DISPATCH_API_TOKEN`); without the token a caller of `/health` gets the state but not paths or reasons. `now_utc` far from the
  server clock needs `DISPATCH_ALLOW_REPLAY=1`. The model is loaded for `DISPATCH_MODEL_ALIAS` (default `paper`) in the lifespan hook; no model = the service starts and `/signal`
  returns `no_model`. A loaded model is never swapped, and it is taken out of service (`model_stale`) if its alias is cleared or moved: the PRD's "a stale model means no dispatch", and D1a's `clear_alias` ("the service then fails closed"). `/attribution` is 501 with a reason while the engine or its inputs are unavailable; with a `price_source` it feeds D1b's engine from the ledger
  (forecasts via D1a's `make_forecast_fn`, skipped for periods over 3 days, as D1b asked).

## 6. Metrics and alerts

Metrics (`dispatch/monitoring/metrics.py`, own registry per `Metrics`): the nine the task named, plus `dispatch_data_age_allowance_seconds{report}`,
`dispatch_capture_baseline`, `dispatch_feature_age_seconds{asset}`, `dispatch_monitor_breaches_total{check}`, `dispatch_monitor_consecutive_breaches{check}`,
`dispatch_audit_errors_total`, `dispatch_redis_writable`. Series that alerts rate over exist from the first scrape. `/metrics` parses with
`prometheus_client.parser` (tested, and in the manual check).

Alerts (`ops/alerts.yml`): DispatchHalted, DispatchServiceDown, DispatchGuardRejectionRate (> 25% of cycles, 15 m), DispatchRedisReadOnly, DispatchAuditWriteFailures,
DispatchCycleLatencyP99 (> 30 s), DispatchStaleData (age over the report's allowance), DispatchFeatureDrift (PSI > `DRIFT_PSI_ALERT` 0.2), DispatchCaptureRateDecay (20% under
baseline), DispatchSlippageOverTolerance (> `SLIPPAGE_TOL` 5%), DispatchAutoHaltApproaching (2 passes in a row). `tests/test_monitoring.py` parses `alerts.yml`, the dashboard
JSON, `prometheus.yml` and `docker-compose.yml`, and fails if a rule or a panel names a metric the service does not export, if panels overlap, if a compose port is public, or if a
compose file mounts something that does not exist. No `promtool`, Grafana or Docker exists here: PromQL was not parsed by Prometheus (only checked for the metrics it uses and
balanced brackets), and the compose file was never started.

Monitoring (FR11): `checks.py` returns `Breach` objects. Stale data watches only the live inputs (NP6-905-CD, NP6-331-CD, NP6-322-CD, NP6-86-CD, NP3-565-CD, NP4-190-CD,
NP4-188-CD; cadence + `DATA_FRESHNESS_TARGET_S` + a 4 h lateness allowance for the daily DAM reports): the yearly archives and the reports adopted once from the research folder
are allowed to be old, and watching them would halt dispatch for nothing. Drift is an in-house PSI per feature (deciles of the reference; NaN is its own bin; categories supported) against
`forecaster.reference_frame`, with Evidently's per-column test as an optional second opinion. `HaltPolicy`: per check, 3 consecutive breaching passes set the halt flag (reason and
`set_by="monitor:halt_policy"`, audit `halt`); a clean pass resets that check; a check that did not run neither counts nor resets; a check that raises is a breach. A drift or capture-decay
breach also records a retrain request (audit `retrain_request`, `trains: false`); nothing trains.

## 7. Gate 3: how it is measured, and the result

Method (`monitoring.checks.gate3`, recipe in `ops/README.md`): replay the same decision times through `run_cycle` (point-in-time features loaded before each call) into a fresh paper
ledger; `gate3(ledger, spec, prices, backtest)` replays the ledger FILE at the realised prices (SOC adds up, every limit holds) and compares its revenue with the backtest's:
slippage = |paper - backtest| / max(|backtest|, $1). Pass = slippage <= `SLIPPAGE_TOL` (5%) and a consistent ledger. `record_gate3_result(result, version)` writes the outcome on the model
version in the registry (D1a's `record_gate3`, which `live` promotion requires) and in the audit log.

Results (`tests/test_monitoring.py`):

* Against D1b's own harness: the real LP (`lp.solve`) inside the cycle, a model with ancillary prices, 60 consecutive 15-minute decisions, `rolling.run_shadow(..., step_intervals=1)` as
  the backtest. All 60 cycles dispatched (the guard accepted every real LP plan, with REGDN/ECRS/RRS/NSPIN awards), **paper revenue = backtest revenue = $2110.95, slippage 0.0**, ledger replay clean,
  per-interval revenue and SOC equal.
* Same, with the fake optimizer: slippage < 1e-9.
* Injected differences all fail: a stale feed every fifth cycle, a guard that interferes (exposure cap), a derated asset (7.5 MW against 10 MW), a ledger edited by hand (the replay says which SOC no
  longer adds up), and the real-LP variant with the cap. Borderline: exactly 5% passes, 6% fails.
* A failing Gate 3 through the monitor runner trips the halt policy after 3 passes.

## 8. What was reused from `resilience/` (read only)

* A setpoint for an interval that has ended is refused the way `EpochDevice` refuses an expired command (the guard's window check), and the ledger's "newer interval, later issue time" rule is its
  `(epoch, seq)` fencing (`stale_interval`, `non_increasing_issue`). The halt flag plays the lease nobody holds: no lease, no command.
* One cycle per asset at a time (a per-asset lock; a second concurrent call gets `cycle_in_progress`), like a lease giving one worker one transformer group.
* `project_soc_end` is a model-free conservation check in the spirit of `resilience/physics/balance.py`, and the ledger replay re-derives the state from the log the way the runtime replay does.
* The crash story (section 4) is the takeover story: the next process starts from the files and reports what the dead one left half done.

Not reused: the lease table itself (one service process per `DISPATCH_HOME`, not workers) and OpenDSS (the referee here is the ledger's own re-check).

## 10. Latency

`tests/test_api.py::test_latency_of_200_cycles`: 200 consecutive cycles with fakes, real audit log and ledger with fsync on, one fresh feature set per cycle: **p50 37.1 ms, p99 50.8 ms, max 86.6 ms**, all 200 dispatched (earlier runs on a busier machine: p50 42 to 44 ms, p99 55 to 78 ms). Through the HTTP layer (TestClient, 100 requests): p50 39.6 ms, p99 45.8 ms.
The target is p99 < 30 s (`CYCLE_P99_TARGET_S`); the platform's own part is a few tens of milliseconds (4 fsynced audit records, 1 ledger line, pandas). With the real LP in the loop (60 cycles,
`gate3` test) a cycle took about 0.2 s; one cold LP solve costs about a second. The model's `predict` and the online store read are what will dominate in production.

## 11. Findings about the environment

* **redis-py 8.1 cannot talk to this machine's Redis 3.0.504 unless the client is told `protocol=2`**: it opens with `HELLO`, which Redis 3.0 answers `unknown command 'HELLO'`.
  `service.state.make_redis_client` sets it; D0's `online.connect` already does.
* **The Redis on localhost:6379 is full.** 108 MB used of a 100 MB `maxmemory`, policy `noeviction`, 23 keys that belong to another application (`AXXESS_API.*`, `VW_*`, 
  `selected_rows`), none of this platform's. Every write fails with `OutOfMemoryError`; reads and `DEL` work. So today `redis-cli SET dispatch:halt ...`, D0's `write_latest` and the audit
  anchor all fail on it. I did not touch those keys or the config. The service surfaces it (`redis_writable`, alert `DispatchRedisReadOnly`) and `POST /kill` still halts (held in the process,
  not persisted). D0 already wrote a `FileStore` fallback for the same reason.
* Evidently takes 10 to 30 s to import; it is only imported inside `evidently_drift` and the one test that uses it.
* The tool shell here mangles some heredocs; every script that matters is a file.

## 12. Known limits and open questions

* One writer per `DISPATCH_HOME`: the audit log and the ledger are single-writer (a lock inside the process, a tail re-read at every append). Two service processes on one directory would be flagged by `verify()`, not prevented.
* The exposure cap is the least-defined limit (PRD: "exposure caps"). The definition above is mine and conservative; it needs a business decision (inventory cost? daily loss? AS shortfall?). When it binds it rejects
  everything until the cap is raised.
* Paper SOC has age 0, so `soc_stale` is exercised by unit tests only; with real telemetry it needs a real source behind `GuardState`.
* A net setpoint cannot express the LP's simultaneous charge and discharge below the price `p*` (D1b: -$113/MWh for the pilot); the ledger would book the net.
* The audit anchor lives in Redis, which today cannot take writes, so on this machine only the chain protects the log. The kill latch does not survive a service restart while Redis refuses writes.
* Capture rate and slippage need a `price_source` and a `backtest_fn`; until they are passed to `create_app` those two checks are skipped and their gauges are NaN. Nothing schedules `/signal`, the feature refresh or
  the monitoring beyond the in-process pass.
* The compose stack, the PromQL and the Grafana JSON were never run against the real programs.
* Retention of the audit log is undecided (PRD open question).
